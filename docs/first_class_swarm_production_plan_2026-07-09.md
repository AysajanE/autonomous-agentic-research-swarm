Status: approved for implementation (design only — no implementation in this document)

## 0. Executive summary

The battle test proved one thing conclusively: **the repo-native control plane works as an audit and provenance substrate**. Contracts, deterministic gates, worktree isolation, run manifests, and review bundles carried a real empirical project from raw data to a released, hash-inventoried artifact bundle, and the two genuine Judge blocks on T080 prove the deterministic firewall is real.

It proved the opposite about everything else. The swarm today is a **controlled execution plane with no brain, no supervisor, no reviewer, and no scientist**:

- **No brain.** Planner is `choose_tasks_heuristic()`. `planner.md` is never loaded by any code path. T035 ballooning into an 8-day, 8-manifest, ~20-repair campaign, and the unplanned T045–T052 chain, are the direct cost.
- **No supervisor.** `loop` is `tick` on a sleep timer. Judging, merging, sweeping, releasing, repair, cleanup, and escalation are all human steps. `@human` markers route nowhere.
- **No reviewer.** The live Judge is four booleans. It approves on manifest *existence* — fabricated `legacy_backfill` manifests and `blocked`-status manifests both qualify. The H055 audit proved a fully Judge-approved frontier can be scientifically wrong (silent vendor-keying, 10/20 stale hashes, red tests) hours after approval.
- **No scientist.** Zero scientific-method content in any prompt. The paper is 63 lines, cites only repo-local artifacts, contains no statistical inference of any kind, and answers a causal-flavored question with a before/after mean around a hardcoded date. W7 writing tasks are contractually denied network access, so a literature review is structurally impossible.
- **And the runtime is not actually autonomous-safe.** Claim detection never matches the runtime's own branch format (`^(T\d{3})\b` vs `T###_slug`), so unattended ticks double-claim and then crash the loop on an uncaught `SystemExit`. 44% of the release's run manifests are backfilled or operator-recorded after manual work.

External evidence (2024–2026 systems and literature; §1–2) says the team's instincts are right and the bar is knowable: the demonstrated ceiling for fully autonomous papers is a **mid-pack workshop paper**; main-track acceptances required human-verified experiments. Citation fabrication runs 18–29% in free generation and is deterministically checkable. LLM judges are usable only with cross-family panels, rubric anchoring, and position discipline. Long-horizon agent reliability decays exponentially, so task granularity and gate density are reliability parameters, not style choices.

**The plan in one sentence:** keep the deterministic control plane byte-for-byte in spirit, split the framework kernel from the project instance, and build five missing layers above it — a coded Supervisor, a real Planner runtime, a layered Judge (deterministic core → scripted science gates → cross-family referee panel → human attestation), a scientific-rigor layer (phased preregistration in all three modes covering analysis *and* data/instance construction, a bidirectional claim–evidence ledger, literature/citation machinery, statistical robustness automation), and a manuscript-production program — delivered as **incremental, eval-gated milestone PR series** (realistic total ≈24–28 engineer-weeks incl. contingency and rehearsal, §10), not as another one-shot 128k drop-in packet.

**Definition of success (next launch):** the swarm executes a full research program in any of the three modes and produces (a) a submission-grade manuscript with verified external citations, real statistical inference (or the modeling-mode analog), and machine-checked claim–evidence links in **both directions**; (b) an AEA-shaped replication package that a clean-room agent can reproduce at the class-appropriate bar; (c) a compliance bundle (venue policy + consent, AI disclosure generated from logs, human-owner attestation with bundle-bypassing spot checks); with (d) every state transition, dollar, and review verdict on the durable record, and (e) a **measured** provenance-defect catch rate from seeded drills — not an unmeasurable "zero incidents" claim. Scientific integrity is the top-priority invariant: **the system must prefer blocking, abstaining, or reporting a negative result over ever manufacturing evidence** — and every mechanism below is designed to make the truthful path the cheap path.

## 2. Verdict on the team's own improvement plan

The ten improvement targets in `corpus/improvement_targets.md` are correct and are all absorbed into this plan. Four structural problems with the pack as it stands:

1. **The delivery vehicle is proven-fragile.** The v1 rewrite's own README documents that three-, four-, and five-stage runner designs all failed on heavy terminal packet stages, forcing a six-stage split — yet the new pack returns to three stages with a single 128k-token terminal packet for a *broader* change (swarm.py 2,197 lines + quality_gates.py 1,508 lines + contracts + prompts + tests). A single non-executable mega-packet authored under `no_tools` (patches that were never run) is the wrong way to change a runtime this stateful. **Replace with milestone PRs, each red/green-tested before the next begins** (§10).
2. **The pack's own dependency is dead.** `/Users/aeziz-local/staged-workflow-runner` no longer exists (the runner lives under `~/keel/tools/staged-workflow-runner/`); every command in the pack README fails as written, and all nine attempted improvement runs sit failed/cancelled at stage 1. The reviewed-runner path stays valuable for frozen high-stakes *review*, but implementation goes through PRs.
3. **Ten targets, but at least eight production-critical dimensions are missing**: literature grounding and citation integrity (explicitly flagged in the retrospective, absent from the targets), statistical-methodology machinery, evaluation/benchmarking of the swarm itself, cost accounting and budgets, model routing and vendor fallback, security/sandboxing, data licensing, and authorship/AI-disclosure policy. All eight are first-class sections below.
4. **Internal tensions**: the `.local` operator runbooks the retrospective called "the right direction" are banned from stage-2/3 authority (this plan ports them to code instead, §4.1); "enforceable changes, not prose" is demanded while several rigor targets have no deterministic check defined — this plan defines, for each rigor obligation, either a deterministic check or an explicit "rubric-only-by-design" label (§6.6); and the pack's own files are partially gitignored — drift-resistance irony.

## 3. Design principles (what is preserved, what changes)

**Preserved — non-negotiable, verified strengths:**

- The repository is the shared memory; coordination through files, contracts, manifests, and git history. No agent-to-agent chat.
- Task-file state is authoritative **for scientific/lifecycle state**; folder placement is projection. Claim/lease *liveness* is authoritative in claim refs, and the task-file claim fields are a projection of the ref — one primitive, one projection rule (§4.1).
- One task, one branch, one worktree; bounded `allowed_paths`.
- Deterministic, offline gates as the merge firewall floor. LLM judgment is *layered above* the deterministic core, never replaces it. Gates whose evidence requires the network are split into a network **refresh step** that writes manifested snapshots and an **offline gate** whose verdict is a pure function of repo state — every historical gate verdict stays replayable (§5.2).
- Durable run manifests and review bundles as first-class outputs. **The execution trace, not the manuscript, is the unit of audit** — the paper is a derived artifact.
- Stop-on-ambiguity discipline: blocking with a precise question is a success mode, and the evaluation program scores it as one (§9.3).

**Changed — structural:**

1. **Framework and project instance are separated** (§4.5): first by configuration extraction (all project literals move behind a declared pack interface), then — as a deliberate, separately-decided step — by physical packaging. The current L2-rent project (the STR / Settlement-Take-Rate battle-test project — one and the same) becomes the first *pack*, kept as the regression reference.
2. **The Operator loop becomes code** (§4.1). Supervision, judging, merging, sweeping, cleanup, repair dispatch, escalation, and budget enforcement run in a coded state machine. Humans supervise the supervisor.
3. **Planner and Judge become real runtime roles** (§4.2, §5). Both keep deterministic cores; both gain contracted LLM passes with structured outputs and bounded authority.
4. **A scientific-rigor layer becomes part of the contract system** (§6): phased preregistration in all three modes covering analysis *and* data/instance construction, a bidirectional claim–evidence ledger, a literature corpus with verified citations, and statistical-robustness artifacts as release blockers.
5. **The manuscript becomes a computed, program-produced artifact** (§7): multi-task analysis and writing programs, venue and authorship contracts, referee/revision loops, and a generated replication + compliance package.
6. **The swarm measures itself** (§9): golden-task regression with a held-out adversarially-refreshed tier, seeded-defect drills with a measured catch rate, eval CI on prompt/contract changes, cost accounting, and KPIs including human-review-hours and defects-found-at-human-gates.

**Explicit non-goals** (rejected after evaluation):

- No orchestration daemon (Dagster/Prefect/Temporal). Their good ideas — asset-first declaration, colocated asset checks, hash-based staleness, durable-execution semantics — are borrowed into the file/git-native kernel. A server contradicts "repo is the control plane" and offline gates.
- No database. Append-only JSONL journals + git provide event history with better auditability at this scale.
- No bitwise-reproducibility stack (Nix) by default. `uv.lock` + digest-pinned container for release verification is the contracted bar; release verification distinguishes **content equivalence** (values/data compared) from **byte identity** (hashes compared) explicitly per artifact class.
- No second *write-path* executor backend before Battle Test 2 (§4.3) — cross-family capability is load-bearing only for review/audit roles, which get purpose-built limited profiles instead.
- **One live research program per repo instance in v1.** Multi-program support is out of scope; the kernel–pack interface reserves program-namespaced claim refs (`refs/swarm/claims/<program>/T###`) as an M5b design consideration so the door stays open (§4.5).
- No autonomous-authorship theater. The system is designed for the strongest honest claim: machine-generated, machine-verified, human-owned science.

### 4.1 The Supervisor (Operator-as-code)

A new `swarm.py supervise` loop (replacing `loop`) implementing the state machine already specified in prose in `.local/prompts/operator_queue_driver_prompt.md` — ported to code, not re-derived:

```
each cycle:
  1. SYNC      guarded fetch/ff of base
  2. REAP      check leases + heartbeats; expired/dead executors → task 'orphaned' note,
               reopen or dispatch repair (never silently 'blocked')
  3. TICK      select ready tasks (respecting WIP caps, budget caps, review-queue backpressure)
  4. JUDGE     auto-invoke the Judge stack (§5) on ready_for_review tasks
  5. MERGE     serial merge queue for approved branches: ff-merge → re-run `make gate`
               + the landed task's gates on the post-merge tree → then and only then done.
               Merge-time enforcement: appends to Operator-owned shared surfaces
               (catalog, registry, releases) must come from Operator-role tasks
  6. SWEEP     projection sweep + verify (folders and claim-field projections)
  7. CLEAN     worktree/branch cleanup for done tasks; `git worktree prune`; stale-branch report
  8. REPAIR    bounded retry dispatch: failed task + structured failure context → rerun
               with --repair-context, max N attempts, then escalate
  9. PLAN      invoke Planner runtime on its triggers (§4.2)
 10. ESCALATE  route @human/@planner events to the notification sink; emit status snapshot
 11. ACCOUNT   append cost/usage events; enforce spend ceilings (§9.1)
```

Mechanics:

- **The claim ref is the atomic primitive.** Claiming pushes `refs/swarm/claims/T###` (compare-and-swap semantics; push rejection = claim lost = skip). The task-file claim fields (`claimed_by`, `lease_id` (monotonic), `claimed_at`, `lease_ttl`) are an **eventually-consistent projection** of the ref, written after the ref, reconciled by the sweep. (`lease_id` is the lease primitive; the term `claim_id` is reserved for the §6.2 claim–evidence ledger — two distinct namespaces.) Precedence on disagreement: ref exists + file says backlog → file is stale, sweep updates it; file says active + no ref → orphaned claim, reap it; journal-only records → advisory. The projection-drift gate covers ref⇔file drift. Workers heartbeat at <50% of lease TTL; missed heartbeats mark the task *orphaned* — a distinct condition from *blocked* (T035's false-blocked pathology becomes structurally impossible to confuse with a scientific block). Merge tooling rejects artifacts stamped with a superseded `lease_id` — git's ff-only requirement is the fencing check.
- **Handoff namespacing.** The blanket handoff-dir carve-out is narrowed: a task may write only `.orchestrator/handoff/H<task_id>_*`, the same way run/review manifests are already namespaced.
- **Session model for long tasks.** Tasks above a declared size run as *resumable sessions*: the executor must maintain a progress file + checkpoint markers (the Anthropic initializer/incremental-session pattern); on death, the supervisor relaunches with the progress file as context rather than restarting. Tasks may not receive a multi-hour timebox unless they declare a checkpoint/resume contract.
- **Escalation is a real channel.** `swarm.py status` renders one honest dashboard (all six states + orphaned, per-task last manifest status, blocked reasons, open `@human` questions, lease health, spend). The supervisor pushes events (blocked, orphaned, budget-breach, judge-escalation, loop-exit) to a configurable sink (webhook/desktop/email) defined in the framework contract. `@human` markers become structured events, not markdown prayers.
- **Crash-only design.** The supervisor keeps no in-memory state that matters: every decision is derived from (repo state ∪ claim refs ∪ event journal) under the precedence rules above, so kill/restart at any point is safe. The event journal is an append-only JSONL under `reports/status/events/` recording every transition with actor, timestamp, and cause — the single source for run replay and post-run retrospectives.

### 4.2 The Planner runtime

Planner becomes an invocable LLM role with **bounded write authority** (only `.orchestrator/backlog/` + `workstreams.md`, all outputs passing task-lint gates before anything can be claimed), triggered by the supervisor:

1. **Program planning (launch).** Given the project contract + protocol + venue profile, the Planner emits the research-program DAG: workstreams, task files, dependencies, and the preregistration artifacts (§6.1). Where competing hypotheses or experiment designs exist, selection uses **pairwise ranking, not absolute scoring** (the co-scientist Elo lesson: relative comparison is the available oracle when no absolute oracle exists), and recurring critique patterns from referee reports feed back into Planner constraints (meta-review loop). Human review of the initial plan is a mandatory gate — the single highest-leverage human hour in the system.
2. **Pre-launch triage (decomposition pressure).** Every task carries a `complexity_tier: S|M|L` and per-tier ceilings (max wall-clock, max expected diff, max tool budget). Any `L` task, and any task the heuristic flags (ETL touching >1 source, >2 declared outputs, first-of-kind task in a workstream), must pass a Planner triage pass that either (a) confirms it as bounded with a written reconnaissance note, or (b) splits it. **The T035 rule:** no task may combine discovery and construction; if reconnaissance discovers the ground truth is unclear, the correct output is a decomposition proposal, not a bigger diff. This is the direct application of the exponential-hazard result: decomposition size is a reliability parameter.
3. **Replanning triggers.** N failed runs (default 2), timebox exceeded, `@planner` escalation from Worker/Judge, or a gate-detected contract conflict → Planner receives the structured failure context and may rewrite/split/retire backlog tasks. **Exception with teeth:** retiring any task linked to a preregistered hypothesis is an L3 human escalation, never a Planner-only decision — a null result must never be laundered into a "failed task" (§6.5). Mid-flight scientific surprises route to Planner + human, never to silent in-task scope widening.
4. **Worker reconnaissance phase.** Task template v2 (§4.4) gives every M/L task a mandatory bounded recon step: scope understanding, risks, decomposition pressure assessment, proposed approach — written to the task file *before* implementation begins, so ballooning is visible at the first review, not after 8 days.

### 4.3 Executor abstraction (descoped) and model families

`_codex_exec_cmd` becomes an **executor interface**, but with deliberately asymmetric scope:

- **One write-path backend** (Codex CLI, as today) carries all Worker/Operator execution through Battle Test 2. Making a second CLI safe as a write-path worker (sandbox parity, network toggles, usage formats, resume semantics, worktree discipline) roughly doubles the runtime-hardening surface for no measured need; it is post-BT2 scope, adopted only on demonstrated vendor outage or worker-quality gap.
- **A second model family (Claude) ships in two limited profiles**: (a) a **read-only, report-emitting profile** (Planner triage and program planning, referee, recall audit) — ships in **M2** for the Planner, extended to referees in M3b; no worktree writes, no resume, no sandbox parity. (b) an **execute-with-scratch-writes profile** for the integrity-audit role (M3b): a fresh disposable worktree, full executor sandbox (workspace-write, network off), **no commit/push rights**, outputs written only to the audit-report surface — the audit must rebuild pipelines and recompute numbers, which a read-only profile cannot do.
- **A third family (e.g., Gemini) is required for the release-path manuscript panel** (referee-only, read-only profile): because the single write-path family (Codex) authors every manuscript section, the family-of-author ban (§5.3) leaves only non-authoring families eligible to vote on the manuscript — with two families total, that is a single voting family, which defeats the panel. Task-level review remains workable with two families (the non-authoring family votes). If the third family is unavailable at release time, the supervisor hard-blocks and escalates to the human gate — never silently waives.

```yaml
executors:
  worker_default:   {backend: codex,  model: <current frontier codex>, sandbox: workspace-write}
  planner:          {backend: claude, model: <top tier>, profile: read-only+backlog-write}   # M2
  integrity_audit:  {backend: claude, model: <top tier>, profile: scratch-worktree, network: off}  # M3b
  referee_panel:    # one vote per family; manuscript panel needs ≥2 non-authoring families (§5.3)
    - {backend: claude, model: <top tier>, profile: read-only}
    - {backend: codex,  model: <frontier>, profile: read-only}     # votes only on artifacts codex did not author
    - {backend: gemini-cli-or-api, model: <frontier>, profile: read-only, required_for: release_path}
```

Requirements: structured usage capture (tokens/cost/wall-clock into the run manifest — basic capture ships in **M1** because the spend ledger needs it), uniform prompt injection, and a `--record-session` transcript artifact. Executor CLI versions are **pinned in the framework contract**; adopting a new CLI or model version requires a golden-suite pass (and referee-role recalibration, §9.5). The family-diversity constraint is enforced by the supervisor from these declarations; when it cannot be satisfied, the supervisor hard-blocks and escalates.

### 4.4 Task schema v2

Frontmatter additions (all linted by a deterministic task-lint gate; MAST says specification defects are the #1 failure class, so the linter is strict). Frontmatter is **immutable during execution** (§4.0 #13):

```yaml
task_kind: etl | analysis | validation | writing | lit_review | model | proof | bridge | ops | integrity_audit | repair
complexity_tier: S | M | L            # ceilings per tier in framework contract
success_criteria:                      # machine-readable; referee must verdict on each
  - id: SC1
    statement: "..."
    verification: "command or artifact pointer"
```

The task file keeps its human-readable markdown body (recon note, notes/decisions, status) — the battle test proved that surface carries real value; only the machine-consumed fields get stricter structure. Task-lint also enforces the **validation-independence rule** (§6.5): a `validation` task must declare a comparison-basis input, by manifest hash, that is disjoint from the construction task's declared inputs.

### 4.5 Framework/instance separation

Two-step, in this order:

**Step 1 (M5a) — configuration extraction, same repo.** Every project literal currently hardcoded in kernel code (rollup registry filename, "Rollup inclusion criteria" heading, `l2_l1_rent_working_paper.*`, panel schema names, W1/W2 semantics, W9 operator boundary, `pyproject` name) moves into pack configuration; `gate_framework_contract` stops pinning "configurable" values to literals; schemas become **executable** (pandera for dataframes, JSON Schema for manifests) with a single source of truth — the doc-shaped YAML + duplicated-Python-literals pattern is abolished. (The executable **hybrid-interface and instance-manifest schemas are the exception: they ship early, in M3a**, because the `hybrid_interface_conformance` gate and the modeling battery need them; M5a generalizes the executable-schema treatment to the remaining contracts.) Framework tests decouple from live paper content (the frozen `EXPECTED_SECTIONS` test and live-release literal assertions are replaced by venue-profile-parameterized fixtures). A `swarm init --mode empirical|modeling|hybrid` scaffold generates a new project pack; the README's currently-fictional "swap the contracts" path becomes real and CI-tested.

**Step 2 (M5b, decision point) — physical packaging.** An installable semver'd kernel package is *conditionally* in scope: it pays off when a second real project exists. Either way, the **kernel–pack interface is versioned now**: the pack manifest declares `kernel_requires: >=X,<Y`; the kernel publishes a machine-readable interface descriptor (task-schema version, manifest-schema versions, gate-registration API version, executor-config version); a preflight gate fails on mismatch; semver policy: any manifest/task-schema field removal or gate-semantics change is breaking. The descriptor reserves program-namespaced claim refs (`refs/swarm/claims/<program>/T###`) for future multi-program support (§3 non-goals).

Modeling and hybrid modes reach **contract parity in the gate engine from the start**: the gate layer is mode-parameterized (per-mode gate matrix, §5.2), `model_spec.md` and `hybrid_interface_v1.yaml` get the executable-schema treatment (instance manifests validated by code; experiment specs with locked solver/seed/budget fields), and modeling golden tasks enter the suite at M3a, not M5. Instance manifests get **two schema variants**: bridge-generated (hybrid; `source_processed_manifests` required and content-bound) and synthetic (pure modeling; generator command, parameter distributions/ranges, seeds, git sha, outputs — `source_processed_manifests` required only in hybrid). The locked experiment-design/instance spec is the contract surface that modeling-mode `etl_decision_log` clause ids resolve against.

## 5. The Judge stack: layered verification

Verification is a stack, cheapest-first; every layer's verdict is a durable artifact. A layer may never be waived by a higher layer. The stack's checklist categories are named after the empirically dominant failure taxonomy (Sakana v1 independent evaluation + Agents4Science findings): **execution-integrity, numeric-provenance, citation-validity, novelty-grounding, structural-completeness, mechanism-consistency**.

### 5.1 L0 — deterministic kernel gates (keep + harden)

Everything that exists today, plus M0 items: recomputed hashes, provenance classes, ownership re-check at judge time, pinned constrained gate commands, frontmatter immutability, projection-drift, content-bound validation, actor separation, task-lint, rule-level diagnostics.

### 5.2 L1 — scripted science gates (new; deterministic verdicts)

Design rule (resolves the offline-principle tension): any gate needing external services is split into a **network refresh step** — a task that writes manifested, timestamped verification snapshots into the repo — and an **offline gate** whose verdict is a pure function of repo state (snapshot present, fresher than the contracted staleness window, status clean). Every release's gate verdicts are replayable offline, forever.

| Gate | Empirical form | Modeling form |
|---|---|---|
| `citation_integrity` | every bib entry has a clean verification snapshot (Crossref DOI → S2/OpenAlex title cascade, fuzzy threshold; retraction status; URL resolution); exact `@key`⇔bib bijection; repo-local citations point at release-inventoried artifacts by hash | same (literature machinery is mode-independent) |
| `claim_evidence_ledger` | every registered claim maps to a live artifact + verification command; no bare numeric literals outside the computed-values mechanism; causal/trend lexicon is an **advisory pre-filter** — type enforcement is referee adjudication (§6.2) | claims map to theorem/proof artifacts, solver logs, or experiment manifests |
| `statistical_reporting` | every estimate in `reports/tables/` carries estimate + SE/CI + N + the prereg-declared VCE; spec-curve artifact present for headline claims; sensitivity (RV/Oster) artifact for causal claims | solver-verification battery: instance-manifest conformance, seed/budget-lock conformance, optimality-gap/convergence reporting, ablation/parameter-sweep artifact over the preregistered experiment grid |
| `prereg_conformance` | **bidirectional**: (a) confirmatory claims match the frozen prereg hash; (b) every preregistered hypothesis maps to a terminal reported outcome (supported / not supported / inconclusive / abandoned-with-reason) in the manuscript or a mandatory deviations appendix | same, against frozen model-spec + experiment-design hash |
| `etl_decision_log` | logged discretionary data-construction choices (keying, inclusion/exclusion, missingness, dedup, outliers) without a matching locked protocol clause id fail; mechanically detectable patterns (zero-fill without a coverage flag) fail; **completeness of logging is audited, not gate-detectable** (§6.5 sampling + seeded drills) | instance-generation decisions log against the locked instance spec |
| `rigor_sections` | W6/W7/analysis tasks and manuscript source contain non-empty, structurally parseable "Evidence table", "Alternative explanations considered", and "Uncertainty statement" sections (presence/shape deterministic; substance is L2's job) | same |
| `text_overlap` | near-duplicate span detection of the manuscript against the full-text literature corpus + general overlap screen; thresholds in the venue contract | same |
| `render_qa` | paper builds from a clean worktree via `make paper`; no `Figure Figure`/`??`/unresolved refs/missing includes; venue limits respected; figure QA (labels/legends present — the Sakana v2 VLM-critic check, scripted where possible) | same |
| `checklist_derivation` | venue checklist answers derived from pipeline artifacts, not asserted (error bars ⇐ generating script computed them; code released ⇐ package exists and runs) | same |
| `replication_package_audit` | AEA-template completeness: master script, README generated from repo state, program→exhibit mapping, environment lock, data availability statements captured at ingest | modeling profile: solver versions, instance sets, seeds, budgets, derivation/verification scripts |
| `hybrid_interface_conformance` *(hybrid only)* | at bridge-task judge time: the emitted instance manifest validates against the executable hybrid-interface schema; every `source_processed_manifests` hash is recomputed against disk (the §4.0 #16 content-binding pattern extended across the bridge); the interface's required pre-bridge empirical validation artifacts existed and were green at generation time. At modeling-task judge time: any declared input resolving outside `contracts/instances/**` manifests fails. Re-run in full at release assembly | — (this gate *is* the mode seam) |

**Hybrid composition rule:** in `mode: hybrid`, gate form is selected **per task by `task_kind`** — `etl`/`analysis`/`validation` tasks take the empirical form; `model`/`proof` tasks the modeling form; `bridge` tasks take the modeling form of `etl_decision_log` (instance-generation decisions vs the locked instance spec) plus `hybrid_interface_conformance`; writing/release-path invocations run the **union** of both forms, with `statistical_reporting` requirements resolved per claim type from the ledger (§6.2); all other task kinds (`lit_review`, `ops`, `integrity_audit`, `repair`) take the mode-independent gate forms. **In the hybrid bridge campaign, experiment-grid execution and counterfactual-analysis tasks are `task_kind: model`** — §6.1's "modeling analysis" means these task kinds; the shipped hybrid template pins this.

### 5.3 L2 — the referee: cross-family LLM panel (new)

- **Task-level substantive review** (all M/L scientific tasks): one referee agent from a family that did not author the artifact loads a **task-kind-specific rubric** (versioned under `contracts/rubrics/`), receives the task contract + diff + run manifest + declared outputs, and must verdict **per success criterion** with evidence pointers, emitting structured findings JSON to `reports/status/referee_reports/`. Binary/coarse verdicts only (supported / not supported / cannot verify) — LLM referees are reliable at coarse decisions and unreliable at fine-grained scoring. Two families suffice at task level.
- **Manuscript-level panel** (release path): 3 referees, aggregated **one vote per model family**. **Family-of-author ban at artifact granularity:** no referee votes on an artifact its own family authored. Since the single write-path family (Codex) authors every section (§4.3), the manuscript verdict requires **≥2 non-authoring voting families** — which is why the third family is `required_for: release_path`; the authoring family's referee participates as a non-voting commenter (its findings still spawn revision tasks). If the constraint cannot be satisfied, the supervisor hard-blocks and escalates — never waives. Rubric-anchored: claims-map verification, identification/confound checks, statistical validity, limitations coverage, citation spot-checks, novelty/positioning against the literature corpus, and **mechanism-consistency** (does the stated explanation match the actual data/logs — the "correct answer, wrong mechanism" check). Position-swapped wherever two artifacts are compared.
- **Against shared blind spots** (family diversity mitigates self-preference, not shared context): (a) each referee must **open the underlying artifacts** for a kernel-sampled subset of claims — not just the author-curated pointers; (b) a mandatory **unregistered-assertion sweep**: one referee pass whose sole rubric is to enumerate every substantive assertion in the full manuscript text and map each to a ledger id — unmatched assertions block release (this closes the qualitative-overclaiming channel the lexicon can't); (c) the §6.5 integrity audit provides the execution-grounded cross-check on a random sample of registered claims, not just headline numbers.
- **Verdict semantics:** "cannot verify" **blocks** — a claim the panel cannot verify escalates to the human gate; uncertainty never defaults to approval.
- **Anti-theater rules:** referees are read-only; findings spawn *revision tasks* through the deterministic task generator (§7.2), not inline edits; a referee report with open major findings blocks `done` for W6/W7 tasks; referee fidelity is measured against a human-graded gold set **that includes deliberately wrong-but-coherent artifacts** (§9.3) before its verdicts gate anything. The agreement bar is **fixed before grading begins**, written into `contracts/rubrics/calibration.yaml` by the human grader (suggested floor: ≥80% agreement with human verdicts on blocking-severity findings; ≤10% verdict flips under position swap); milestone criteria evaluate against that committed file.

### 5.4 L3 — human gates (explicit, few, high-leverage)

**Four release-blocking attestation gates plus one standing escalation channel**, each consuming a structured evidence bundle (rubric-first summary: gates run + outcomes, claims + artifact pointers, deviations, open questions):

1. Research-program plan approval (after Planner launch pass).
2. Preregistration locks — every phase (§6.1: empirical 2a/2b, modeling experiment lock, hybrid Lock A/B) — and any amendment.
3. Integrity-audit sign-off before release assembly (§6.5).
4. Release + submission attestation by the named human owner (§7.4, §8).
5. *(channel, not a gate)* Escalations: judge disagreement, budget breach, blocked-with-@human, unsatisfiable constraints, hypothesis-task retirement.

**The attestation gate is designed against rubber-stamping** — the bundle is swarm-authored, so the owner's checklist includes mandatory *bundle-bypassing* checks: (a) k registered claims, **sampled by the kernel** (not chosen by the swarm or the owner), traced from manuscript text to primary artifacts directly; (b) one headline number independently recomputed from the replication package on the owner's machine; (c) the raw referee disagreements read in full (not the aggregated verdicts). "Defects surfaced per human gate" is a tracked KPI; a sustained zero triggers process review, not celebration.

**Full human-touchpoint budget** (the KPI denominator counts each item once): the four attestation gates; amendment reviews (= gate 2); escalation events by class (= channel 5); milestone-PR review during the build; referee gold-set grading (scheduled, with hours, in M3b); merge-conflict resolution. Review-queue backpressure is enforced: `ready_for_review` has a WIP cap; the supervisor stops dispatching new work rather than growing an unreviewable pile.

## 6. The scientific-rigor layer ("the swarm always seeks truth")

The battle test's deepest scientific failures — measurement-layer HARKing (protocol tolerances amended mid-run by the actors whose validations were failing), circular validation (checks that pass by construction), silent undercounting degraded to `rent=0` "data", an unfalsifiable descriptive claim in causal clothing, and a self-referential bibliography — are all *incentive and machinery* failures, not model-capability failures. The countermeasures below are designed bidirectionally: not just "registered claims must have evidence" but "assertions must be registered, hypotheses must be reported, and discretionary choices must be declared."

### 6.1 Preregistration semantics for the protocol (phased, in all three modes)

`docs/protocol.md` (and its modeling analog, the model-spec + experiment-design pair) is upgraded from "locked definitions" to a **preregistration contract** covering *both layers where forking paths live* — with a phased lock in every mode, because a single all-at-once lock is either blind (locked before data contact) or HARK-prone (locked after):

- **Empirical two-phase lock.** Phase 1 — an *ingest/profiling window*: raw acquisition and schema-profiling tasks may run pre-lock but may not write processed/panel surfaces; the **data-construction protocol** (entity resolution/keying rules, inclusion/exclusion criteria, missingness policy with zero-fill banned absent an explicit coverage flag, dedup rules, outlier handling, sample-window trimming) is drafted from profiling evidence and locked (**gate 2a**) before any panel-construction ETL task may claim. Phase 2 — the **analysis plan** (hypotheses; primary/secondary metrics; estimators, VCE choice, clustering dimension, kernel/bandwidth; break-detection hyperparameters; the declared specification space for robustness **including the spec-curve survival threshold**; stopping rules; tolerances as point values) locks (**gate 2b**) before any analysis task may claim. ETL tasks log every discretionary choice against a protocol clause id (`etl_decision_log` gate). Amendments driven by phenomena discoverable only post-construction get the same human-gated relief valve as modeling re-confirmation below.
- **Modeling preregistration** (pure modeling programs): registered conjectures/propositions with directional predictions; the locked experiment grid (instance-set spec, seeds, solver/budget fields, convergence tolerances, and the content-equivalence tolerances per artifact class); the sweep survival criterion. **Two-phase lock:** the model spec may iterate freely during theory development until the **experiment lock**; after it, the amendment machinery below applies. **Gating (pure modeling):** `proof` and model-formalization tasks may claim during the pre-lock theory phase; the experiment lock gates all experiment-execution and analysis tasks and any task registering a `computational` claim. **Modeling re-confirmation is defined and always available:** proofs re-verified plus experiments re-run on freshly drawn seeds/instances not used in the amendment decision — so a routine model iteration never strands the whole program in permanent-exploratory status.
- **Hybrid two-stage lock:** Lock A (simultaneous with the analysis-plan lock, gate 2b) freezes the model spec and the experiment design *parametrically* over the instance-manifest schema — grid dimensions, seeds, solver/budget fields, and counterfactual definitions expressed as functions of the to-be-estimated parameters. Lock B (after bridge tasks emit instance manifests, before any modeling-analysis task may claim) hashes the concrete instance-set binding. Binding estimated parameters through the frozen functional form is **not** an amendment; changing grid shape, solver, seeds, or counterfactual definitions is. Gating: the empirical locks (2a/2b) gate empirical tasks as above; Lock A gates bridge and model tasks; Lock B gates modeling analysis (`task_kind: model`, §5.2) and any task registering a `counterfactual` claim — **enforced at judge time**: any ledger entry typed `counterfactual` must reference the Lock B hash record, and the `claim_evidence_ledger` gate fails counterfactual entries registered before Lock B exists.

Each lock file is **content-hashed and timestamped at lock time** by the supervisor. Amendments are versioned with effective dates and mechanically expensive in exactly the right way: an amendment task must (a) rerun the full validation suite under both old and new definitions and publish the sensitivity delta, (b) be reviewed by a human principal assisted by a different model family than the requester, and (c) tag all downstream claims as exploratory until re-confirmed. **Amendment cap:** two per program; further amendments require the L3 human gate with written justification that enters the disclosure bundle. **Re-confirmation is defined per mode:** it requires evidence not used in the amendment decision — empirical: a subsequent time window, held-out sample, or new source; modeling: freshly drawn seeds/instances; hybrid: whichever layer the amendment touched. Where no such evidence can exist, the exploratory tag is permanent. **Headline rule:** abstract/headline claims must be confirmatory; if the primary result is exploratory, the release is re-typed an *exploratory report* with mandatory title-page labeling and a dedicated human sign-off. Infinite cheap reruns until significance — HARKing at machine speed — is the credibility killer for automated research; these rules convert it into a mechanically checkable property.

### 6.2 The claim–evidence ledger (bidirectional)

A machine-readable `contracts/claims.yaml` (or per-paper `claims/` dir): every substantive claim destined for the manuscript is registered with a `claim_id`, statement, type, supporting artifact(s) by hash, verification command, and uncertainty artifact.

- **Actors are named:** the authoring Worker drafts claims; **claim type is adjudicated by a different-family referee (or the Planner), never self-assigned** — a Worker cannot type a causal claim "descriptive" to dodge the identification requirements.
- **Taxonomy** (extended for mode generality and calibrated risk): `descriptive | associational | causal | interpretation | methodological | theoretical | computational | counterfactual | literature`. Type drives requirements: `causal` → identification-strategy + sensitivity artifacts; `interpretation` → the strictest referee scrutiny (Kosmos: interpretation statements are the least reliable class); `theoretical` → a per-claim **proof artifact** (e.g., `reports/proofs/<claim_id>.md` or a keyed manuscript-appendix anchor), hash-registered in the ledger, with a machine-verification companion where feasible (symbolic check, or numeric falsification of stated inequalities/comparative-statics signs on kernel-sampled parameter points) — else covered by the `referee_derivation_pass` row of the §6.6 table; `computational` → solver logs + seed/budget/instance conformance; `counterfactual` (hybrid — claims combining an empirical estimate with a model-derived result) → the **union** of both layers: empirical estimate artifacts with CIs + the prereg clause estimating them, the instance-manifest id + hash, the experiment manifest/solver logs with conformance, and the cross-bridge uncertainty artifact (§6.4) — a referee may never type such a claim `computational` or `causal` alone, which would silently drop one layer's requirements; `literature` → verified citation + alignment evidence (§6.3). The paper's own empirical claims must trace to pipeline artifacts — never to a model's assertion.
- **Uncertainty artifact, per claim type** (so the ledger's required-field check has defined behavior everywhere): `descriptive`/`associational`/`causal` → CI + measurement-uncertainty band (§6.4); `computational` → seed-replication dispersion + optimality-gap/convergence evidence; `counterfactual` → the cross-bridge band (§6.4); `theoretical` → an assumption-scope statement (the conditions under which the proposition holds) in lieu of a numeric artifact — explicitly N/A-for-CIs by design; `interpretation` → N/A-for-numeric-artifacts by design; required instead: an evidence-scope statement listing the registered claim ids the interpretation rests on (each of which must carry its own uncertainty artifact); `methodological`/`literature` → N/A with a justification field.
- **Both directions are enforced:** registered→evidenced by the `claim_evidence_ledger` gate; asserted→registered by the referee's unregistered-assertion sweep (§5.3); preregistered→reported by bidirectional `prereg_conformance` (§5.2).

### 6.3 Literature machinery (new workstream, W-Lit)

- **Acquisition:** network-enabled `lit_review` tasks with the same provenance discipline as ETL: fetched sources snapshotted (URL/DOI, retrieval date, sha256 of abstract/PDF) into an append-only corpus `data/raw/literature/<date>/` with manifests. Search strategy (databases, queries, inclusion criteria) is declared in the task contract — a mini-PRISMA for auditability.
- **Recall audit (against the search-blindness failure mode):** a second, independently derived search — different model family, different query set, different database mix — whose retrieved set is diffed against the corpus; non-trivial uncovered clusters escalate to the human before related-work synthesis completes. The novelty review is only as good as corpus recall, and this is the only mechanism that tests recall.
- **Synthesis:** related-work tasks may cite only corpus entries; BibTeX is *generated from the corpus*, so every external bib entry carries machine-verifiable retrieval evidence.
- **Verification:** the `citation_integrity` gate runs offline over refresh-task snapshots (§5.2). Each literature claim carries its citation key **plus a quoted evidence span that must string-match into the snapshotted source** (deterministic, blocking). The LLM claim–citation **alignment referee is advisory**: its findings spawn revision tasks but do not block (entailment at gate quality is an open research problem; the deterministic layer already kills the observed failure mode — fabricated/self-referential citations). Human spot-checking of alignment is folded into the L3 manuscript gate. Workers get the verification tool during drafting (the 6–79× self-correction result: capability beats exhortation).

### 6.4 Statistical rigor as artifacts, not prose

For empirical mode (modeling mode's analog battery is defined in the §5.2 gate matrix):

- **Inference module** in the kernel's analysis toolkit (a real, scheduled deliverable — milestone M3c): HAC/Newey-West, Driscoll-Kraay (with a large-T guard gate), clustered and two-way SEs; formal break estimation (Bai-Perron-class via `ruptures`) against any imposed date; bootstrap CIs. Estimator choices come from the preregistration; the `statistical_reporting` gate verifies produced tables used the declared VCE.
- **Specification-curve/multiverse artifact** (RobustiPy-class) over the *preregistered* grid — which **includes top-k data-construction variants** (alternative keying, alternative missingness handling), not just analysis-layer choices, so an ETL-layer bias cannot shift every curve point identically without appearing in the grid. Headline claims are release-eligible only with an attached curve artifact meeting the prereg-locked survival threshold.
- **Sensitivity artifact** for causal claims: robustness values (Cinelli–Hazlett RV) / Oster bounds, benchmarked and thresholded.
- **Cross-bridge uncertainty (hybrid):** where headline claims depend on model outputs calibrated from empirical estimates, the preregistered grid must include parameter perturbations spanning the empirical estimates' CI band (or a bootstrap-over-instances design declared at Lock A); the resulting counterfactual band is the mandatory uncertainty artifact for every `counterfactual` claim. A model calibrated to point estimates alone cannot pass — the modeling battery would be green while the combined claim carried no uncertainty at all.
- **Regime/break dating is a dedicated manifested pipeline stage** whose outputs downstream tasks consume by hash — never re-estimated ad hoc inside analysis code.
- **Uncertainty propagation:** every released headline statistic carries a CI artifact plus a measurement-uncertainty band derived from known coverage gaps (registry caveats auto-propagate into a generated limitations section — the Arbitrum/Linea caveats silently dropped from the battle-test paper become structurally impossible to drop).

### 6.5 Validation independence and the institutionalized adversarial audit

- **Independence rule:** every validation check must compare against data or logic *not used to construct* the artifact under test. Enforced two ways (per the §6.6 labeling): deterministically where declarable — task-lint requires `validation` tasks to declare a comparison-basis input by manifest hash, disjoint from the construction task's declared inputs (§4.4) — and by referee rubric for logical independence. Self-referential checks (vendor key coverage passing by construction; identities re-verifying the ETL's own SystemExit assertions) are reclassified as build-time invariants, not validations. Protocol-promised cross-checks are either implemented or formally struck via an amendment. Vendor API response metadata (ETag/Last-Modified, retrieval timestamps) is captured into raw manifests at ingest; single-source denominators are flagged in the risk register and a second source is contracted where one exists.
- **Integrity-audit task kind** (institutionalizing H055): a mandatory pre-release task, executed by a *different model family* than the primary builders (the §4.3 scratch-worktree profile: full sandbox, no commit/push, outputs only to the audit surface), in a fresh worktree: rebuild canonical surfaces from manifests, recompute headline numbers **and a kernel-sampled random subset of registered non-headline claims** independently, hash-compare against the release inventory, and **sample discretionary ETL decisions generically against the data-construction protocol** — a forward-looking audit brief, not a replay of the battle-test failure list. **The audit brief is mode-parameterized.** Modeling form: re-run a kernel-sampled subset of experiments from instance manifests + locked seeds (compared within the declared tolerance classes), independently re-derive a kernel-sampled subset of theoretical claims (findings recorded in the audit report), sample instance-generation decisions against the locked experiment spec, and hash-compare `reports/models/` + proof artifacts against the release inventory. **Hybrid form = the union of the empirical and modeling briefs, plus seam audits:** regenerate a kernel-sampled subset of instance sets from `source_processed_manifests` via the recorded generator command and compare against the committed instances at the declared per-artifact-class bar (byte identity by default inside the pinned container), and re-run a sampled experiment-grid cell. Release assembly is blocked on its pass. Post-approval repairs must flow through numbered tasks — the H056 out-of-band-branch pattern becomes a gate violation.
- **Negative results cannot be silently dropped:** bidirectional `prereg_conformance` (§5.2) forces every preregistered hypothesis to a terminal reported outcome; retiring a hypothesis-linked task is an L3 human escalation (§4.2); the registered-vs-reported hypothesis ratio is a KPI (§9.3). Null and negative results are first-class release outcomes with the same manuscript machinery.
- **Abstention is scored as success:** the evaluation program explicitly measures correct-blocking (precision/coverage split), and prompts state it: a Worker that blocks with a precise question outperforms a Worker that guesses.

### 6.6 The truth-seeking charter (prompt + contract surface)

Role prompts are rewritten around the scientific method (scheduled in M3b). **Enforcement labeling (explicit, so this section cannot drift into prose-only):**

| Obligation | Enforcement |
|---|---|
| Evidence table, alternative-explanations, uncertainty-statement sections present and non-empty | deterministic (`rigor_sections` gate) |
| Claim–evidence alignment | deterministic (ledger gate) + referee sweep |
| Claim typing honesty | referee adjudication (rubric-backed; golden-tasked) |
| Theoretical-claim derivation validity (no feasible machine-verification companion) | `referee_derivation_pass` — rubric-only by design (L2, `proof_review` rubric), human-sampled at L3, independently re-derived by the §6.5 audit |
| Validation independence | deterministic where declarable (task-lint disjoint comparison-basis inputs, §4.4) + referee rubric for logical independence |
| ETL decision-log completeness | deterministic for logged-entry↔clause-id matching and mechanically detectable patterns (zero-fill); unlogged-choice detection via §6.5 audit sampling + seeded drills |
| Evidence ranking, hedging discipline, alternative-explanation *substance* | rubric-only by design (L2), human-sampled at L3 |
| No fabricated provenance | deterministic (provenance classes, actor separation, hash recomputation, log persistence) + seeded-drill detection rate (§9.3) |

The absolute prohibition stands: any manifest, citation, number, or review not derived from a real execution is the one unforgivable defect class — and the machinery above makes fabrication *harder than honesty*.

## 7. The manuscript-production program

### 7.1 The computed paper

- Analysis emits `paper_values.json` — every reportable statistic keyed, typed, with units and uncertainty. The manuscript references keys; a gate bans bare numeric literals. "Figure Figure 1" class defects die in `render_qa`.
- The paper reads pre-computed, manifested artifacts by hash (Quarto render stays cheap, deterministic, offline); a full-execution render from a clean worktree is a release gate.
- Manuscript sources (`index.qmd`, `references.bib`, `_quarto.yml`, venue/authorship contracts) join the release inventory; render-manifest input hashes are re-verified at release. Data panels join the release inventory and catalog artifact roots (closing the audit's release-perimeter gap).

### 7.2 W7 as a program, not a task

Task chain template shipped with the kernel: **contribution-claims map** (from the ledger) → **outline lock** (contract) → **per-section drafting tasks** (each with the claims map + literature corpus slice as inputs) → **integration** → **referee panel** → **revision cycle** (referee findings deterministically generate scoped revision tasks with the finding as repair context) → **compliance + package assembly**. Draft milestones (`paper_v1..vN`) are DAG nodes; acceptance = zero open major referee findings + all gates green. The Anthropic failing-first registry pattern applies: every required section/exhibit starts `failing` in a paper registry and flips only on verified completion — "a figure-only slice is not a release" becomes mechanical.

W6 (analysis) is likewise a program: estimation plan → estimation → robustness battery (§6.4) → exhibits, with the exhibits manifest (id, builder, inputs, caption, notes) as the analysis→paper interface, and figure self-QA (labels, legends, units) at exhibit build time.

**All program templates are mode-parameterized** (the Planner must never improvise a mode's program shape — MAST says specification defects are the #1 failure class). Pure modeling ships two chains: a *theory program* (model formalization → proposition registration in the ledger → proof tasks → derivation-check pass → statement of results) and a *computational-experiment program* (experiment plan from the locked grid → solver/simulation runs → sweep battery → exhibits). Hybrid ships the *bridge campaign* (calibration inputs → bridge/instance generation → experiment-grid execution over seeds → counterfactual analysis → exhibits; grid-execution and counterfactual-analysis nodes are `task_kind: model`, §5.2). All chains share the exhibits manifest as the analysis→paper interface, with modeling outputs keyed into `paper_values.json` exactly like empirical ones.

### 7.3 The replication package (generated, then audited)

An Operator release task generates the AEA-shaped package from repo state: raw+analysis data (or documented access instructions for restricted sources, captured at ingest), all transformation code, master script, and the Social Science Data Editors template README **rendered from artifacts** (package versions from `uv.lock`, runtimes from run manifests, exhibit mapping from the catalog, data statements from raw manifests). The `replication_package_audit` gate scripts the machine-verifiable criteria; ACM badge tiers become named release levels — "Functional" (Judge bar) and "Reproduced" (clean-room re-run by a non-author agent). Release verification declares, per artifact class, whether the bar is **byte identity** (hash match; requires the digest-pinned container) or **content equivalence** (values/data compared) — the two are never conflated.

**Empirical Reproduced levels, per data-availability class:** open data → full raw→results traversal from packaged/archived snapshots; restricted/licensed or metered data → traversal from the sha256-verified cold-storage raw archives under owner credentials, with the public package carrying access instructions plus a processed→results clean-room run and an AEA-style partial-reproducibility statement generated into the README. §8 item 3 accepts the class-appropriate bar — it is never quietly redefined per release.

**Modeling profile:** solver names/versions, instance manifests, seeds, budgets, convergence/optimality logs, and derivation-check scripts replace the data-package core. A **solver-availability statement** (license class, plus an open-solver fallback configuration or instance subset for the Reproduced-level clean-room run — proprietary solver licenses cannot ship in the container) mirrors the empirical restricted-data pattern; content-equivalence tolerances for solver outputs come from the preregistered experiment design; the README generator handles the no-data case.

**Hybrid profile:** the union — empirical core ∪ modeling profile ∪ bridge artifacts (instance-generator scripts, instance manifests, the hybrid-interface contract) — with `replication_package_audit` verifying the cross-layer hash chain end-to-end (processed manifests → instance manifests → experiment outputs), and the clean-room Reproduced run required to *traverse the bridge* (regenerate instances from source manifests), not merely consume committed ones.

Raw-snapshot retention gets a contract with teeth: each as-of snapshot archived (tar+zstd) to versioned cold storage, archive URL + sha256 recorded in the raw manifest, gate fails on unresolvable pointers. (The battle test's raw evidence layer — 135,648 manifested files — no longer exists anywhere; the existing release is amended with an explicit `raw_evidence_unavailable` note (§4.0), and that class of loss becomes impossible to ship silently going forward.)

### 7.4 Venue, authorship, disclosure — and consent

- `contracts/venue.yaml`: target venue, format engine/template (Quarto→LaTeX class), page/word limits, anonymization, reference style, required statements, the venue's AI policy, **and the venue-consent status** (whether the venue knowingly accepts AI-generated submissions, with evidence). The Zochi/Carl episode made this concrete: undisclosed AI submission is treated by the community as co-opting peer review — **no submission package is emitted without a consent-compatible venue policy on record**.
- `contracts/authorship.yaml`: human author(s) of record, CRediT-style contribution statement including AI roles, AI-use disclosure text, data/code availability. Front matter renders from it; the swarm is documented in the disclosure, never in the author field (ICMJE/COPE/Nature/Science compliance).
- **Disclosure is generated from execution logs** (models+versions per role, gate outcomes, human-edit history), not from a model's memory — simultaneously the compliance evidence and the audit log, and exactly the artifact NeurIPS-style appeals now demand.
- Two release modes selected at program start: `mainstream` (human owner, human-substantive verification pass, AI as disclosed assistant) and `ai_native` (Agents4Science-class venues; full autonomy, full transparency). The release gate refuses to emit a submission package whose mode conflicts with the venue policy on record.

## 8. What "submission-ready" means (the honest definition)

Calibrated against 2026 outcomes (autonomous ceiling ≈ mid-pack workshop; main-track required human verification; CodeScientist's funnel: only ~1/3 of machine-flagged discoveries survived human validation — expect and budget for aggressive filtering):

A release is **submission-ready** when all of the following artifacts exist and are green:

1. Manuscript with: externally grounded related work whose **coverage is attested by the recall audit** (§6.3 — not a citation-count floor), registered claims all gate-checked in both directions, real inference artifacts and/or modeling-battery analogs behind every headline claim (for claims depending on both layers, joined by the cross-bridge uncertainty artifact, §6.4), **headline claims confirmatory** (else the release is re-typed an exploratory report, §6.1), a clean `text_overlap` screen, and generated limitations covering all registered caveats, in venue-compliant format.
2. Internal referee panel: no open major findings; zero unresolved "cannot verify" verdicts; rubric outcomes at or above the contracted bar (calibrated to ≈ "weak accept" on the target venue's scale via the gold set).
3. Replication package at the class-appropriate "Reproduced" level (§7.3; clean-room agent re-run succeeded).
4. Integrity-audit pass + bidirectional preregistration conformance report.
5. Compliance bundle: venue AI-policy **and consent** check, generated disclosure, human owner's signed attestation **including the bundle-bypassing spot checks of §5.4**.

Item 5 is not a concession — it is the design. The swarm's job is to make the human's verification hour *decisive*: everything reviewable in one evidence bundle, every claim one click from its artifact, and the kernel — not the swarm — chooses which claims the human spot-checks.

## 9. Operations, economics, and self-evaluation

### 9.1 Cost and budgets
Per-run usage (tokens, wall-clock, estimated USD, tool calls) captured from executors into run manifests (basic capture lands in M1 with the spend ledger); per-task budgets in frontmatter; per-program and per-loop ceilings in the project contract; supervisor enforces (warn → throttle → block → escalate). BigQuery and any metered externals get per-call byte/spend caps and env-var-scoped billing projects. A `swarm.py costs` report aggregates per task/workstream/model (M1).

**Recurring operational line items (budgeted, not just named):** referee-panel tokens (3 referees × manuscript reviews × revision cycles — the dominant recurring cost; scope L2 to M/L tasks and the release path); citation refresh tasks (Crossref/OpenAlex/S2 are free-tier; the cost is task time); literature full-text storage (corpus snapshots, typically single-digit GB); raw-snapshot cold storage (project-dependent — the STR project's raw layer was hundreds of GB; the archive target decision in §11 is also a budget decision); seeded-drill and golden-suite eval runs at milestone gates. Planning-grade order-of-magnitude estimates (to be replaced by M1 spend-ledger actuals): tier-(c) live-LLM eval runs ≈ low tens of dollars per milestone gate; M3b gold-set calibration ≈ one-to-low-hundreds of dollars of referee tokens plus the scheduled human grading hours; BT2 Stage A ≈ a few hundred dollars; BT2 Stage B is a real research program budgeted in its own project contract (§10).

### 9.2 Model routing
Contract-encoded, per the executor table (§4.3): top tier for Planner/referee/protocol-touching work; the single write-path workhorse for bounded execution; scripts before models for deterministic transforms; never downgrade decision authority for cost or availability. Fan-out only for genuinely parallel breadth (data pulls, literature sweeps, per-panel analyses, spec-curve grids); synthesis (protocol interpretation, manuscript integration) stays single-context — the multi-agent token multiplier only pays for breadth.

### 9.3 The evaluation program (the swarm measures itself)
- **Golden-task suite, two tiers:** (a) a **CI-visible set** (20–50 tasks harvested from the battle test's real failures: the T035 recon/decomposition scenario, task-lint on known-bad files, Judge-must-reject-fabricated-manifest, claim-regex round-trip, "reproduce table X from manifests alone", citation gate on a poisoned bib, a causal claim paraphrased without trigger words and typed "descriptive", correct-blocking scenarios, lock-machinery tasks (pre-lock claim refused; amendment without dual-definition rerun blocks; exploratory headline re-typed), and **a per-mode minimum once M3a lands: ≥5 modeling tasks** (false-lemma block via the numeric-falsification checker, seed/budget-lock violation, instance-conformance failure, sweep-artifact-missing block, correct-blocking on an ambiguous model spec) **plus bridge-adversarial tasks** (an instance manifest with a stale `source_processed_manifests` hash blocks; a modeling task with a direct `data/processed` input blocks; a post-generation instance edit is caught by hash recompute)); and (b) a **held-out set**, run only at milestone gates and refreshed adversarially each milestone with new tasks targeting the *current* mechanisms — the CI set is the optimization target for prompt evolution, so the held-out set is the Goodhart control.
- **Seeded-defect drills (fabrication is measured, not asserted):** the drill harness (scheduled in M5) periodically injects a known-fabricated manifest/citation/claim into a rehearsal run; the pipeline must catch it. The drill rotation spans modes: at least one proof-defect drill (a subtly false lemma) and one tampered-seed/instance drill alongside the empirical fabrication classes. The KPI is **catch rate**, replacing the unmeasurable "zero fabrication incidents" — zero *detected* is not zero.
- **Verification tiers** (every acceptance criterion in §10 is annotated with one): (a) per-PR deterministic CI; (b) nightly/on-demand soak + chaos harness (kill -9 drills, orphan reaping, 24h runs); (c) pre-milestone live-LLM eval runs (Planner/referee golden tasks; metered, non-deterministic, run on demand — never per-PR). A **mock/replay executor backend** (records/replays executor transcripts) is an M1 deliverable — the precondition for executor-involving tier-(a) tests (M2 onward) and all tier-(c) runs; M0/M1 kernel tests use scripted git fixtures and a trivial stub.
- **Judge calibration:** a human-graded gold set including **deliberately wrong-but-coherent artifacts** (not only past reviews — 21 of 23 historical reviews are box-ticking approvals and would teach the referee nothing) and ≥3 wrong-but-coherent proofs; referee panels are scored against it (agreement, position-stability) against the pre-committed bar in `contracts/rubrics/calibration.yaml` (§5.3) before their verdicts gate releases, and periodically thereafter. Gold-set grading hours are scheduled work in M3b.
- **KPIs on the durable record:** stage pass rates *and* end-to-end release rate (expect the latter to lag by an order of magnitude — the field-wide composition gap); rework rate per task class; false-block and false-ready rates; **seeded-defect catch rate**; **defects surfaced per human gate** (sustained zero → process review); **registered-vs-reported hypothesis ratio**; human review-hours per released artifact (denominator = the full touchpoint table of §5.4); cost per artifact. Post-run retrospectives are generated from the event journal, and routing/decomposition defaults are tuned from these measurements, not vibes.

### 9.4 Security and unattended-safety
The AGENTS.md §8 boundary becomes mechanical (**scheduled: M1**, except where noted): preflight verifies containment (marker + refusal if user-level credentials beyond a scoped deploy key and fine-grained repo token are readable); gates run constrained (§4.0 #12, M0); network policy enforced at the executor *and* gate layer with the effective network state recorded per run as a first-class manifest field; `danger-full-access` sandbox mode requires an explicit double opt-in (`--i-accept-full-access` flag **and** task-level `allow_network`) and is recorded in the manifest; a static gate rejects gate-command strings containing `curl`/`wget`/`http(s)://` in non-network workstreams. Prompt-injection posture (**M3b**, with W-Lit): fetched web/vendor content is data, never instructions — lit-review and ETL prompts carry the standard quarantine framing, and network-enabled tasks run with write scopes no broader than their `allowed_paths`. Secrets never in the repo; scoped injection at launch; spend caps as the blast-radius limiter of last resort. A one-time recorded **vendor-policy compatibility check** for long-running unattended autonomous use joins the M1 preflight.

### 9.5 Lifecycle and maintenance (steady state)
- **Model/CLI changes:** executor CLI versions and role models are pinned in the framework contract. Adopting a new version requires a golden-suite pass; for referee roles, additionally a gold-set recalibration against `calibration.yaml`. **Within a research program, model versions are held fixed**; a mid-program swap is an amendment-class event (reviewed at gate 2, logged, downstream results flagged).
- **Cadences and owners:** citation-verification snapshots refreshed per the contracted staleness window and always at release; cold-storage archive integrity (hash spot-checks) quarterly; dependency/lockfile updates through normal PR flow gated by the golden suite; referee recalibration after any model change and at each battle test.
- **Prompt/behavior drift:** prompt changes are CI-gated (§9.3); behavior drift under *fixed* prompts from vendor-side model updates is why versions are pinned and why the held-out suite runs at every milestone and battle test.

The reviewed staged-workflow-runner remains available for *frozen design review* of milestone specs — not as the implementation vehicle (fix its dead path first if used at all).

**Mode-coverage honesty clause:** the framework may claim "production" only for modes exercised in a live battle test. **Regardless of Stage B's mode, a bounded Modeling Battle Test (model-spec lock → submission-ready bundle on a small theory + computational question) is a named precondition before the swarm accepts a pure-modeling program** — hybrid exercises the computational and bridge surfaces but not the theory-program chain (proof tasks, `proof_review` panel on live propositions, the two-phase lock, synthetic instances).

**Pivot criteria (architecture-level).** The team pre-commits to reopening the §3 non-goal decisions (file/git-native kernel, no daemon, no database) if either: supervisor-reliability failures persist across two consecutive soak/battle runs after their failure-path retries, or review backpressure permanently saturates the human owner (WIP cap pinned at zero dispatch for a sustained period despite touchpoint-budget compliance). Absent those signals, the architecture stands.

## 11. Risks and open decisions for the team

1. **Scope discipline for M5.** The single biggest schedule risk. Mitigation: configuration extraction is last, after behavior is pinned by the golden suite; physical packaging is a separate decision that pays off only with a second real project.
2. **Referee cost vs value.** Panels on every task would be ruinous; the plan scopes L2 to M/L scientific tasks and the release path, with the §9.1 budget line making the spend visible. Tune from measured rework-catch rates.
3. **Third-family availability.** Task-level review is workable with two families (the non-authoring family votes); the **manuscript panel requires a third family** because the write-path family authors every section (§4.3/§5.3). Trialed in M3b; if unavailable at release time, the path is hard-block + human escalation, never waiver.
4. **Denominator/source risk is scientific, not framework.** The STR project's single-source vendor denominator remains a validity ceiling no framework fixes; Battle Test 2's question should be chosen with data independence in mind, and §6.5 now requires second sources where they exist.
5. **Human-owner bandwidth.** The full touchpoint table (§5.4) is the real budget, not the four gates; ~6 human-hours for the manuscript gate alone, plus gold-set grading in M3b. The owner is decided no later than M3b (§10 staffing).
6. **Upstream CLI/vendor churn.** The kernel depends on specific executor-CLI behaviors (resume, sandbox flags, usage output). CLI versions are pinned with an upgrade gate (§4.3, §9.5); vendor-policy compatibility for unattended use is checked at M1 preflight (§9.4). Breaking upstream changes mid-build are absorbed at milestone boundaries, not mid-milestone.
7. **Open decision — venue strategy for Battle Test 2:** mainstream venue (human-substantive mode) vs Agents4Science-class (AI-native mode). Changes the W7 program shape and consent requirements; a project-contract input at program start.
8. **Open decision — archive target** for raw snapshots and the replication deposit (institutional storage vs openICPSR vs Zenodo): licensing terms of vendor data (growthepie et al.) must be captured at ingest either way, and may constrain redistribution to access-instructions-only. This is also a §9.1 budget decision.
9. **Open decision — physical kernel packaging (M5 step 2)** and repo home: mono-repo (kernel + first pack) vs split. The versioned interface descriptor is built either way.
